# Identity Service

- PostgreSQL owns `users`, `user_roles`, `store_memberships`, `refresh_sessions`, `verification_tokens`, and `security_events`.
- Email addresses are trimmed and lowercased for uniqueness. Passwords require 8–128 characters, at least one lowercase letter and one punctuation or symbol character. They use Argon2id with 19 MiB memory, two passes, and one lane.
- Email verification is required. New accounts remain pending until their one-time email link is confirmed. The runtime rejects `REQUIRE_EMAIL_VERIFICATION=false`; an active account with no `email_verified_at` cannot sign in and can request a new verification link.
- Access JWTs expire after 10 minutes. Every authorized API request resolves the session family in PostgreSQL, so logout and reset invalidate access immediately.
- Refresh tokens are 256-bit random opaque values. Only SHA-256 verifiers are stored. Rotation inserts a new row and revokes the previous row in one transaction. Reuse revokes the entire family and queues `RefreshReuseDetected.v1` for a future notification consumer.
- Verification links expire after 15 minutes. Password reset uses a six-digit email OTP valid for 10 minutes, with five incorrect attempts per code; the stored verifier is an HMAC keyed by `IDENTITY_MAIL_KEY`. Resending invalidates earlier links or codes. IP and account rate-limit windows last 15 minutes.
- Seller authorization needs both a `seller` role and an active membership for the requested `store_id`. Catalog records membership events in its outbox and retries a secret-protected internal Identity API to update this projection idempotently. Never accept a seller role or membership from public registration input.
- Identity writes `UserRegistered.v1`, `UserEmailVerified.v1`, and `RefreshReuseDetected.v1` to `identity_outbox` in the same transaction as the state change. A worker delivers configured events to Engagement Notification by authenticated webhook with retry and source/id deduplication; Kafka is not used in the local stack.
- Email delivery uses an AES-256-GCM encrypted database outbox. The request does not wait for SMTP. Failed deliveries retry with backoff; after ten failures an operator must investigate. A token that expires before delivery can be replaced through resend. The service does not log token values.
- Verification links carry the one-time token in the URL fragment so the token is not sent in HTTP requests or Referer headers. The frontend removes the fragment after loading. Password reset emails contain the OTP in the message body; the code is never placed in a URL.
- Cookie-changing POST endpoints require the configured exact browser Origin. Deploy only behind HTTPS in production; configure the gateway to preserve and validate the Origin header.
- Deploy the frontend and identity API on the same site so SameSite=Strict refresh cookies work. If running behind a trusted reverse proxy, set `TRUSTED_PROXY_IP` to its socket IP so rate limiting uses its forwarded client IP.
